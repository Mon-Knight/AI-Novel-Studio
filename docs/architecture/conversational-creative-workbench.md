> 状态：v3.6.0 发布候选；对话工作台、决定/审阅授权、章节原子采用、五类桌面结构化原子应用与旧 UI 收敛已实现；未列入白名单的结构化类型及浏览器回退仍失败关闭

> 当前版本：v3.6.0

> 文档职责：定义对话式创作工作台的产品边界、交互模型、运行时职责与分阶段落地顺序

## 1. 决策摘要

AI Novel Studio 的未来主界面将从“作品管理首页 + 章节编辑器中的多个 AI 面板”演进为**以对话驱动任务、以作品承载事实、以产物确认控制写入**的创作工作台。

```text
创作工作台
└─ 小说项目
   └─ 任务对话
      ├─ 用户目标与引导
      ├─ AI 回复与工具调用
      ├─ 一次或多次执行
      ├─ 候选产物
      └─ 确认、审阅与应用决定
```

核心决策如下：

1. **工作台是第一个界面，也是产品中心。**
2. **小说是工作台内的项目。** 小说仍是领域数据的最高级对象，工作台不是新的业务父实体。
3. **项目下的每个对话就是一个独立任务。** 任务可被引导、暂停、恢复、失败重试和单独选择模型。
4. **多个任务可以并发。** 例如一个任务生成下一章，另一个任务审计既有章节；两者拥有独立上下文、模型、状态和产物。
5. **工具调用直接显示在对话中。** 不另设“对话与执行时间线”“任务计划”“工具详情”或“产物详情”面板。
6. **任务完成后在对话中推送专用产物卡片。** 候选结果不会直接写入小说正式事实。
7. **确认与应用采用类似代码变更审查的事务逻辑。** 确认对象、基线版本、变更摘要、冲突与应用结果都必须明确。
8. **原写作工作台保留为人工审阅与编辑界面。** AI 能力迁入对话工作台后，旧工作台只保留阅读、显式编辑、保存与采用等基础能力。
9. **导航中的“待确认”与作品详情中的“待确认产物”删除。** 待处理状态由任务列表徽标、对话消息和产物卡片承载。
10. **提供“当前插件”只读视图。** 用户可以按功能插件、模型插件和其他插件查看运行时实际加载的插件、版本、状态与所提供能力，但不能在该视图安装、卸载、启停、更新或配置插件。
11. **首阶段实现只覆盖 v3.3.0 最小闭环，不修改旧工作台的既有能力边界。**

当前版本已实现：默认创作工作台路由、启动骨架与后台恢复协调、最近有效任务恢复、任务搜索/重命名/归档/恢复、目标与首回合原子创建、任务对话/回合/运行/工具事件/产物卡片持久层、领域候选工具内联投影、任务级模型快照、按任务隔离的 Worker/取消边界、切换任务时后台运行隔离、重启后中断运行事实收敛、Runtime Registry 只读插件投影及发送前精确目录重验、产物来源/基线/校验证据、产物决定/审阅授权、章节候选的授权审阅与原子采用、`outline / character_candidates / event_candidates / setting_candidates / chapter_summary` 五类桌面结构化原子应用、精确 `generic_json / context_compression` 上下文压缩应用，以及写作工作台审阅收敛。目录重验只证明条目来自当前 Runtime 投影；进入桌面 DSH 的模型任务会在创建 Run 前另行执行可取消的原生 tool-call nonce 探针，只有精确 `provider/model` 证明通过才冻结证据并继续。旧生成类 AI 面板、独立实验面板和草稿历史生产入口已移除。

结构化应用不是任意类型的通用入口：桌面端对五类领域产物及精确匹配 `artifactType=generic_json`、`derivationType=context_compression` 的候选执行“领域写入 + append-only `ArtifactDecision`”单一 Rust/SQLite 事务；质量/风格报告、其他 `generic_json`、未知类型和浏览器回退继续稳定拒绝并保持零领域写入。章节正文仍使用独立的 `ReviewAuthorization + adopt_review_authorized_draft` 原子链路。v3.6.0 候选还完成了 Canonical 1A-A/B/C/D 的 Catalog、Facade、Projection、共享 Manifest 和漂移门禁，但四项均为 `catalog_only + partial`，模型可见数为 `0`。

## 2. 设计目标与非目标

### 2.1 目标

- 用户可以用自然语言表达创作目标，而不是先学习一组分散的表单和功能按钮。
- AI 可以根据任务调用既有小说领域工具，逐步完成读取、检索、生成、检查和候选构建。
- 用户可以在同一小说内并行推进互不相同的任务，也可以跨小说切换任务。
- 每个任务可以独立选择 AI 模型，且执行状态不会互相覆盖。
- 工具错误、模型错误、验证错误和应用冲突都出现在发生位置，用户能够理解任务停在哪里。
- 所有正式写入都经过可审计的产物确认与领域事务，保留“用户控制方向与最终采用权”。
- 已有写作、作品详情、Planner、Tool Registry、Result Artifact、Safe Apply、Memory 与 DSH 能力可以渐进迁移，而不是一次性重写。
- 运行时能力通过稳定的能力接口与 Provider 组合，后续可以替换或增加小说上下文压缩等实现，而不改写工作台主流程。
- 用户可以通过只读视图确认当前实际加载了哪些功能、模型和内部插件；显示结果直接来自运行时 Registry，不维护第二份前端插件清单。

### 2.2 非目标

本设计借鉴 Harness/Codex 类工作台的交互方式，但不建设通用软件工程 Agent。规划范围不包括：

- 通用代码编辑、Shell、Git、工作树、插件安装/卸载/启停/配置/更新、插件市场或任意 MCP 管理界面；
- 展示模型的内部思维链或隐藏推理；
- 在界面中复制完整运行日志、任务计划树或独立工具调试器；
- 让 AI 绕过确认直接修改正式正文、人物状态、设定、大纲或 Memory；
- 一次性替换现有数据库、章节工程或所有旧页面；
- 为追求“像 Harness”而引入与小说创作无关的复杂功能。

## 3. 信息架构

### 3.1 三层用户心智

| 层级     | 用户理解               | 主要职责                                       |
| -------- | ---------------------- | ---------------------------------------------- |
| 工作台   | 所有创作任务的入口     | 浏览项目、切换任务、查看并发状态、创建任务     |
| 小说项目 | 一本小说及其正式事实   | 约束任务上下文、承载章节/大纲/人物/设定/Memory |
| 任务对话 | 一项目标的一段持续会话 | 接收引导、执行工具、形成产物、完成确认与应用   |

“工作台”是 UI 聚合层，不改变“小说是领域最高级对象”的数据原则。全局工作台只引用小说和任务，不拥有或复制小说正式事实。

### 3.2 任务、对话与运行

- **任务（Task）** 是用户可见的工作单元，例如“生成第 18 章”或“审计第 1—10 章人物一致性”。
- **对话（Conversation）** 是任务的主要交互载体。产品文案可统一称为“任务”，避免让用户区分两个概念。
- **回合（Turn）** 是一次用户输入以及随后的 AI/工具响应。
- **运行（Run）** 是一个回合触发的可取消执行。线性重试复用原 user Turn 并产生新 Run，不追加重复用户消息、不覆盖旧运行事实；当前以相同 `turnId` 下的稳定 Run 顺序表达 attempt 关系，不伪造显式父子分支。
- **工具调用（Tool Call）** 是运行中的领域动作记录。
- **产物（Artifact）** 是可以被审阅、确认或应用的不可变候选结果。

### 3.3 默认进入路径

```text
启动应用
→ 打开创作工作台
→ 恢复最近小说与最近任务
→ 用户继续任务或新建任务
```

作品管理不再是启动后的中心页面，但“小说作品”能力继续保留，作为项目创建、项目级浏览和人工管理入口。

## 4. 主界面布局

### 4.1 核心布局

```text
┌───────────────┬──────────────────────────────────────────────┐
│ 项目 / 任务树 │ 任务标题、项目、模型、运行状态              │
│               ├──────────────────────────────────────────────┤
│ 小说 A        │ 对话消息                                     │
│  ├ 生成第18章 │ 工具调用行                                   │
│  └ 审计前10章 │ 错误与恢复操作                               │
│ 小说 B        │ 产物卡片                                     │
│  └ 完善大纲   │                                              │
│               ├──────────────────────────────────────────────┤
│ 新建任务      │ 模型选择 / 输入框 / 发送或停止               │
└───────────────┴──────────────────────────────────────────────┘
```

界面保持 Windows 桌面应用风格：紧凑、稳定、浅色、克制边框，避免后台管理仪表盘式卡片堆叠。

当前实现把 Codex 式“紧凑任务树 + 居中对话 + 底部常驻 Composer”与 Harness 式“按回合投影运行、工具、错误与产物”组合：应用导航使用 56px 图标轨，任务树保持稳定宽度，正文流设阅读宽度上限，2K 下不把文字拉成超长行。加载骨架、流式点和状态过渡使用 120–180ms 的克制动效，`prefers-reduced-motion` 下关闭非必要运动。

启动与恢复不得再把整个工作台变成等待面。项目/任务恢复、旧上下文整理和模型目录刷新都显示为局部准备状态：任务树和输入框先可见，草稿始终可编辑，弹窗可取消；只精确禁用依赖未就绪上下文/模型的提交动作。本地问候与能力问答不受这两项准备门禁影响，但必须显示和持久化为 `ans-local` 来源。

### 4.2 左侧项目与任务树

左侧只承载导航和状态概览：

- 小说项目名称、封面缩略图或简化图标；
- 项目下的任务标题、最近活动时间和状态标记；
- 运行中、需要用户操作、失败和已完成的轻量徽标；
- 新建任务、重命名、归档、恢复和删除入口；
- 任务搜索与必要的状态筛选。

左侧不展示任务计划、工具列表、运行步骤详情或产物详情。

### 4.3 中央对话区

中央区域按发生顺序显示：

1. 用户指令或引导；
2. AI 的面向用户说明；
3. 内联工具调用状态；
4. 发生位置对应的错误；
5. 完成后的产物卡片；
6. 用户的确认、退回、修改或应用结果。

对话区是唯一的任务细节入口。产品不另设“对话与执行时间线”“任务计划”“工具”“产物详情”四个并行面板。

### 4.4 输入区与模型选择

- 模型选择器固定在输入区附近，当前任务的选择始终可见。
- 用户可以在发送前更换当前任务模型；更换只影响后续运行，不追溯改变既有消息和产物。
- 运行开始时冻结 Provider、模型 ID、模型参数与价格快照，确保审计和重试可解释。
- 任务级选择优先于项目默认，项目默认优先于应用默认。
- 若模型不支持任务所需能力，发送前给出明确兼容性提示，不静默切换。

### 4.5 当前插件只读视图

工作台提供一个类似 Harness 的“当前插件”查看入口，只用于解释当前 Runtime 已装载的能力。它不是任务工具面板，也不是插件管理中心。

```text
当前插件
├─ 功能插件
├─ 模型插件
└─ 其他插件
```

列表项显示插件名称、分类、版本、简短说明和 `loaded / failed / unavailable` 状态。点击后显示只读详情：功能插件列出其提供的工具或领域能力，模型插件列出其提供方与当前可用模型，其他插件列出其运行时职责。

该视图必须直接读取当前 Runtime 的 Plugin/Capability Registry，不在 React 中硬编码插件名单；它不提供安装、卸载、启停、配置、更新、权限、市场或项目绑定操作，也不显示任务计划、执行时间线或某次任务的工具详情。任务实际发生的工具调用仍只在对应对话中显示。

## 5. 任务创建与引导

### 5.1 创建入口

用户可通过以下方式创建任务：

- 在小说项目旁点击“新建任务”；
- 从工作台的模板入口选择常见任务；
- 在作品或章节的上下文菜单中“在工作台中处理”；
- 从产物卡片继续创建修订或后续任务。

### 5.2 最小任务输入

新任务至少绑定：

- 小说项目；
- 用户目标；
- 初始模型；
- 可选目标章节、章节范围或资产范围。

### 5.3 引导方式

工作台提供领域引导，但不强迫用户填写复杂向导：

- 快捷模板：生成下一章、审计章节、完善大纲、检查人物一致性、整理设定、润色候选；
- 上下文提示：当前章节、最近采用内容、未完成的前置条件；
- AI 澄清：只在关键目标或范围无法确定时提问；
- 完成建议：产物处理完后建议下一步，但不自动创建或执行任务。

## 6. 内联工具调用设计

### 6.1 显示原则

工具调用以紧凑状态行插入对话，不显示隐藏推理。每一行至少包含：

- 工具语义名称与稳定技术名称；
- 目标对象摘要；
- 当前状态；
- 耗时；
- 可展开的安全输入摘要、结果摘要或错误信息。

首批关键调用包括：

```text
读取小说上下文     novel.read_context
读取章节大纲       chapter.read_outline
检索长期记忆       search_memory
生成章节候选       generate_chapter
```

实际 Registry 名称可以在实现任务中适配，但用户可见语义和审计记录必须稳定。

### 6.2 状态

```text
queued → running → succeeded
                 ↘ failed
                 ↘ cancelled
queued/running   → skipped（因前置失败而未执行）
```

### 6.3 错误呈现

错误必须附着在出错调用或生成步骤上，而不是只显示一个全局“任务失败”：

- 读取失败：显示失败的来源与可重试动作；
- 权限或能力缺失：说明需要的项目/章节/模型能力；
- Provider 失败：显示可公开的错误分类和重试状态；
- 校验失败：说明候选未形成产物的原因；
- 基线漂移：提示重新读取上下文并重新生成或重新验证；
- 取消：保留已完成的只读调用，未完成步骤标记取消或跳过。

错误详情不得泄露 API Key、完整敏感请求、内部隐藏提示词或模型思维链。

## 7. 产物卡片

### 7.1 产物出现时机

产物卡片只在候选完成持久化并通过结构校验后推送。流式文本、临时预览或未通过校验的结果不伪装成可确认产物。

### 7.2 通用结构

每张卡片包含：

- 产物类型与标题；
- 目标小说、章节或资产；
- 生成任务、运行和模型；
- 基线版本或修订号；
- 变更摘要、关键指标与验证状态；
- 状态：待处理、需修订、已确认、应用中、已应用、冲突、已拒绝或已失效；
- 主要操作：查看、要求修改、确认、应用、拒绝；
- 应用完成后的正式对象链接。

产物正文可在卡片中预览，并按需打开专用审阅界面；不另设全局“产物详情”页作为主流程。

### 7.3 产物类型与动作

| 产物类型           | 主要处理方式                              | 当前是否写入正式事实                  |
| ------------------ | ----------------------------------------- | ------------------------------------- |
| 章节正文候选       | 确认进入审阅 → 人工审阅/编辑 → 原子采用   | 只有显式“采用”后                      |
| 大纲/人物/设定候选 | 查看差异 → 确认 → 请求应用                | 桌面白名单事务成功后写入              |
| 章节事件/总结候选  | 查看差异 → 确认 → 请求应用                | 桌面白名单事务成功后写入              |
| 审计报告           | 查看 → 追问 → 创建修复任务                | 否，报告本身不应用                    |
| 修订建议           | 选择建议 → 生成新候选                     | 否                                    |
| 小说上下文压缩候选 | 查看 → 确认 → 应用为新 ContextRecord 版本 | 仅精确 `context_compression` 派生类型 |

### 7.4 确认与应用语义

“确认”与“应用”是两个不同动作：

- **确认**表示用户认可某个不可变候选及其基线，可授权下一阶段处理。
- **应用**表示系统通过权威领域事务把已确认候选写入正式事实。
- 章节正文必须先确认进入人工审阅，再由用户显式采用；桌面采用事务同时复验并消费 `ReviewAuthorization`。
- 桌面端允许 `outline / character_candidates / event_candidates / setting_candidates / chapter_summary` 以及精确 `generic_json / context_compression` 申请应用；Rust 在同一 SQLite 事务内完成来源、作用域、基线和幂等校验、领域写入及 append-only 决定。浏览器回退、质量/风格报告、其他 `generic_json` 与未知类型不调用领域写入。
- 重复点击必须幂等；同一决定不能生成两次正式写入。
- 若正式对象修订号已变化，应用失败并进入“冲突”状态，不以最后写入覆盖。
- 修订请求产生新产物或新版本，旧产物保留审计关系但不可被悄然替换。
- 候选卡片持久化与任务进入 `waiting_user` 必须属于同一事务；未决候选优先于 Run 的完成、失败、取消和重启恢复状态。
- `reject / request_revision` 在其他候选均已处理后回到待命；章节 `confirm` 在审阅授权签发后仍等待用户，只有真实章节采用事务完成才可收敛为完成；稳定应用冲突收敛为失败。

## 8. 章节正文的双阶段采用

章节正文是最高风险的用户内容，采用以下明确路径：

```text
任务生成章节候选
→ 对话中推送章节产物卡片
→ 用户“确认并进入审阅”
→ 旧写作工作台打开该不可变候选
→ 默认只读审阅
→ 用户可显式进入人工编辑
→ 用户保存人工修改
→ 用户显式“采用为正式正文”
→ Rust/SQLite 单一事务复验并消费 ReviewAuthorization、采用草稿并收敛任务状态
```

约束：

- 未在对话中确认的 AI 章节候选不能进入采用路径。
- 打开审阅不会自动保存或采用。
- “编辑”“保存”“采用”三个动作需要有不同的状态和反馈。
- 人工直接创建或编辑正文的既有能力继续保留，不强制经过 AI 任务。
- 草稿历史可以作为底层审计事实保留，但旧工作台不再提供“草稿版本查看”入口。

## 10. 并发模型

### 10.1 用户可见规则

- 同一小说可以同时运行多个任务。
- 不同任务拥有独立模型、消息、运行、取消控制和产物。
- 用户切换任务不会取消后台运行。
- 草稿、Composer 错误、压缩候选和局部忙碌状态按任务隔离；后台完成或失败只能写回发起它的任务。
- 任务列表实时显示运行、等待用户、失败和完成状态。
- 应用关闭后，持久任务按明确策略恢复、暂停或标记中断，不伪造成功。

### 10.2 冲突与资源治理

| 场景                         | 处理规则                             |
| ---------------------------- | ------------------------------------ |
| 两个任务只读同一小说         | 允许并发                             |
| 两个任务生成不同候选         | 允许并发，分别冻结基线               |
| 两个任务准备修改同一正式对象 | 允许生成，应用时按 revision CAS 裁决 |
| 同一产物重复应用             | 幂等返回既有结果                     |
| 不同产物竞争同一基线         | 首个成功后，其他产物进入冲突/过期    |
| Provider 达到全局并发或预算  | 任务排队或失败关闭，不绕过治理       |
| 用户取消单个任务             | 只取消该任务的活动运行               |

### 10.3 初始实现边界

首个版本不追求无限并发。建议先支持至少两个独立任务并发，并在以下约束下扩展：

- 只读工具可并发；
- 候选生成可并发；
- 正式写事务短时、单目标、受 revision 和全局治理保护；
- DSH 若仍以“取消即重启进程”工作，则每个活动任务使用独立 Worker/进程边界，避免取消一个任务影响另一个任务；
- 应用级 AI 请求策略继续控制全局并发、频率、Token 与成本。

## 11. 运行时职责边界

### 11.1 目标分层

```text
Workbench Shell（导航与任务视图）
  ↓
Task Conversation Service（消息、回合、模型快照）
  ↓
Task Runtime / Worker Pool（执行、取消、恢复、事件流）
  ↓
Planner + Tool Registry + Provider Pipeline
  ↓
Artifact Service（不可变候选与验证）
  ↓
Decision / Review Authorization / Safe Apply
  ↓
Novel Domain Services + SQLite 权威事实
```

### 11.2 Harness 源码流程的借鉴边界

Harness 的可借鉴主流程是“启动组合能力，运行时按回合循环，界面从事件投影”，而不是复制其代码开发功能：

```text
Profile / Bundle / Patch
→ 装载 Plugin Graph
→ 创建带作用域的 Session / Agent
→ turn/start
→ pre-step：冻结本步骤模型，组装系统提示词、上下文与工具
→ step/start
→ 模型流式输出并提出工具调用
→ 工具策略、并发调度、执行与结果校验
→ 结果回到下一 step
→ 无后续工具调用时 turn/end
→ Session Event 投影为对话、错误和产物卡片
```

对应官方源码入口包括 [Architecture](https://github.com/deepseek-ai/deepseek-harness/blob/141eb6fef83422698aef7a981029e843e8161534/docs/architecture.md)、[Agent Loop](https://github.com/deepseek-ai/deepseek-harness/blob/141eb6fef83422698aef7a981029e843e8161534/packages/core/agent-loop/src/agent.ts)、[Tool Pipeline](https://github.com/deepseek-ai/deepseek-harness/blob/141eb6fef83422698aef7a981029e843e8161534/packages/core/tools/src/index.ts)、[Session](https://github.com/deepseek-ai/deepseek-harness/blob/141eb6fef83422698aef7a981029e843e8161534/packages/core/session/src/index.ts) 与 [Compaction Transaction](https://github.com/deepseek-ai/deepseek-harness/blob/141eb6fef83422698aef7a981029e843e8161534/packages/compaction/compaction-basic/src/region.ts)。该仓库仍处于 Developer Preview，本文冻结的是可迁移原则，不把其内部 API 直接变成 ANS 的长期产品契约。

AI Novel Studio 映射时，一个任务对话对应一个持续 Session/Agent；小说 ID 构成领域 scope；不同任务可以驻留并并发。当前步骤冻结模型和 Provider，切换选择只影响后续步骤或回合，不能拆分已经发出的请求。

模型凭据不进入 Session Event、任务对话或冻结快照。当前应用进程只在内存中按 `scope + providerId + baseUrl + modelId` 保存精确绑定；旧 Run 必须使用其冻结模型身份解析同一会话凭据，任一字段不匹配即失败关闭。退出应用后凭据自然失效，设置切换不得把已加载 Key 携带到另一模型。

Harness 式追加日志承担执行重放与 UI 重建，但不能成为小说事实源。章节、大纲、人物、设定、Memory 和采用状态继续以 ANS 领域服务与 SQLite 为权威；事件只保存稳定引用、安全摘要和必要快照。

### 11.3 能力与 Provider 接口

工具、模型、上下文组装和压缩应遵循“能力定义 → Provider 实现 → Runtime 消费”的稳定接口。插件可以提供或替换实现，任务运行必须冻结实际使用的能力 ID、Provider、版本和配置摘要。

模型目录不是 tool-calling 能力证明。桌面 DSH 启动模型任务时，ANS 必须先在同一 Worker 和 governed proxy 上对精确 `provider/model` 执行一次无副作用 nonce 工具 schema 探针。只接受唯一原生 `tool-call`、参数精确回显 nonce 且 finish kind 为 `tool-calls` 的正证据；失败不缓存、不创建 TaskRun/Turn/Tool/Artifact/Session 领域事实，取消必须终止 Worker 并结算请求治理租约。成功证据可在同 Worker 内缓存 10 分钟，Worker 重启后必须重新探测；Rust 严格验证后只把协议、身份、时间、缓存与 finish/调用计数证据冻结进 `modelSnapshot.runtime.toolCallingAttestation`，不持久化 nonce、usage、原始错误或凭据。探针仍使用 `ai_request_reservations` 执行必需的请求预留与结算审计；这项治理事实不得冒充任务运行事实。

首批领域工具仍是 `novel.read_context`、`chapter.read_outline`、`search_memory` 与 `generate_chapter`。只读工具可以受限并发；候选生成形成 Result Artifact；正式写入保持排他并经过 Decision、revision CAS 与 Safe Apply。工具结果及其产物引用来自结构化结果，不从 AI 回复正文中解析。

这里的旧 Workbench 工具名属于现有 legacy 执行链，不等于 v3.6.0 Canonical `novel.read / structure.read / context.read / memory.search` 已向模型暴露。Canonical 四项当前只完成宿主验证，`modelVisibleToolIdentities=[]`。

上下文压缩必须区分：

- **任务对话压缩**：压缩某个 Session 的历史，用于控制模型输入，可以采用 Runtime 的自动 compaction；
- **小说上下文压缩**：处理正式人物、剧情、伏笔、世界观等知识。Provider 生成带 `derivationType=context_compression` 的可验证 `generic_json` 候选；桌面端按正式来源重算覆盖与基线，并在单一 Rust/SQLite 事务中停用旧活动版本、写入新 ContextRecord 与 append-only 决定。其他 `generic_json` 仍不具备该权限。

“小说 Memory”还必须区分两类实现：migration 026 的 `memory_documents / memory_chunks / memory_embeddings / memory_retrieval_logs` 是桌面 SQLite 长期事实；`NovelMemoryManager`/`NovelMemoryStateUpdater` 的 `Map` 是进程内兼容/实验状态，重启即丢失。后者不能作为长期 Memory、重启恢复或 Canonical `memory.search` 已稳定的证据。

因此后续更换小说上下文压缩方法时，应替换对应 Provider，而不是改写 Agent Loop、工作台或小说权威写入链路。

### 11.4 Harness 源码复用方式

推荐把固定版本 Harness 作为 **Headless Runtime / Worker** 使用，通过 ANS 自己维护的 Adapter 接入，而不是完整 Fork Harness、嵌入其 Web UI，或把其内部类型直接暴露给产品层：

```text
ANS Workbench / Task Conversation Service
  ↓ ANS DSH Adapter（稳定协议）
DSH Worker Pool
  ├─ Session / Agent Loop
  ├─ Tool Pipeline / Scheduler
  ├─ Model Provider
  ├─ Session Compaction
  └─ Plugin Graph
  ↓ ANS Novel Tool Adapter
Novel Domain Services / Artifact / Safe Apply / SQLite
```

可以复用的源码职责包括：Profile/Bundle 组合、作用域 Session/Agent、Turn/Step 循环、工具策略与调度、模型选择、追加事件、对话历史压缩和多 Session 驻留。ANS 继续自行实现小说项目归属、领域工具、全局预算、Result Artifact 转换、用户决定、revision/CAS、Safe Apply 和正式小说数据。

当前发布载体固定 `47f943859bef60e4160492346772ded9b24f765a`，而本设计分析参考 `141eb6fef83422698aef7a981029e843e8161534`。开始实现前必须先审计两个提交之间的 Boot、Agent Loop、Tools、Session、Compaction 和 Plugin API 差异，选择并继续固定一个集成基线；未经独立版本任务、构建和回归验证，不把较新 master 直接替换进发布载体。

一个任务对话映射为一个持续 DSH Session/Agent。若所选固定版本仍以进程重启实现取消，首期使用每个活动任务独立 Worker 或等价故障隔离；后续可以优化 Worker 复用，但不得让取消或崩溃跨任务传播。

“当前插件”视图通过 Adapter 聚合 DSH Plugin Graph 与 ANS 注册的小说能力，再输出稳定的只读 `CurrentPluginProjection`。React 不直接依赖 Cordis/DSH 内部对象，DSH 内部 API 变化也不能迫使 UI、SQLite schema 或历史运行事实同步变化。

### 11.5 权威边界

- React 只呈现事件和发起命令，不自行判定任务或应用成功。
- Runtime 负责任务生命周期、事件顺序、取消与恢复，不拥有小说正式事实。
- Tool Registry 是能力白名单，不允许对话直接调用任意服务或 SQL。
- Artifact Service 负责不可变候选、来源、基线与验证证据。
- Safe Apply 和领域服务负责正式写入、CAS、幂等与审计；当前已完成章节授权采用与五类白名单结构化原子事务，未列入白名单的类型不得借用这些入口。
- SQLite 是桌面端权威事实；LocalStorage 只用于明确的浏览器开发回退。
- DSH 或其他外部 Agent Runtime 可以负责规划与工具编排，但不成为事实权威、预算权威或最终采用者。

### 11.6 事件投影

对话中的工具调用、错误和产物卡片是持久执行事实的 UI 投影。刷新或重启后应由事实重建，而不是依赖内存中的临时消息。

事件至少需要稳定标识：项目、任务、回合、运行、工具调用、产物和决定。流式增量可以短暂存在，但完成、失败、取消和产物形成必须持久化。

## 12. 逻辑数据模型

本节只定义未来需要表达的事实，不在本次文档变更中创建表或 migration。

### 12.1 新增逻辑聚合

| 聚合                | 关键事实                                             |
| ------------------- | ---------------------------------------------------- |
| TaskConversation    | 所属小说、标题、状态、默认模型、最近活动、归档状态   |
| ConversationTurn    | 用户输入、AI 用户可见回复、顺序、创建时间            |
| TaskRun             | 回合、模型/Provider 快照、状态、取消、恢复、用量引用 |
| ToolCallEvent       | 工具名、安全参数摘要、状态、耗时、错误、结果引用     |
| ArtifactDecision    | 产物、用户决定、决定版本、基线、时间、应用引用       |
| ReviewAuthorization | 章节候选获准进入审阅的单次授权与消费状态             |

### 12.2 复用既有事实

- `ResultArtifact` 继续作为候选产物核心，不建立第二套产物真相源。
- 既有 Agent 运行、步骤、工具调用和成本事实应优先扩展或投影，不盲目复制。
- 既有内容事务、revision、Safe Apply、章节草稿与采用记录继续承担正式写入审计。
- 对话消息可以引用产物和工具事实，不把完整大对象重复嵌入多张表。

### 12.3 不变量

1. 每个任务只属于一个小说项目。
2. 每次运行只属于一个回合，并冻结其模型选择。
3. 每次工具调用只属于一个运行，终态不可被改写为另一结果。
4. 每个可应用产物都引用明确基线和目标。
5. 每次用户决定都引用不可变产物版本。
6. 每次正式应用都可追溯到产物、决定、目标 revision 和事务结果。
7. 删除或归档任务不级联删除已经应用的小说事实或审计记录。

## 13. v3.6.0 候选现状与剩余差距

工作台交互目标已经落地：应用默认进入任务工作台，任务/回合/运行/工具事件/产物卡片可持久化，模型快照与任务隔离存在，工具/错误/产物在对话内展示，当前插件来自 Runtime Registry；同一 user Turn 的多次 Run 逐次保留，未决候选可靠投影为等待用户，任务切换不会串用草稿、错误或压缩候选。写作工作台已收敛为章节审阅/编辑器，旧 AI 面板和草稿历史生产入口已移除。

- 五类领域产物及精确 `generic_json / context_compression` 已具备领域写入与 append-only 决定同事务；质量/风格报告、其他 `generic_json`、未知类型及浏览器结构化应用仍失败关闭；
- 短口令单章 Writer 已能读取世界、规则、主角、全书/分卷/章节大纲、风格、输出、研究资料和紧邻前章采用稿；空白项目会进入有序资产恢复，依次生成候选并等待用户显式应用世界与规则、主角和全书规划，规划应用后原子建卷建章并恢复最初正文目标，后续“继续写”在章节审阅、采用和自动总结闭环后推进到下一章；这仍是 ANS 确定性编排，不等同于真实 Main Agent 或 Writing SubAgent 自主运行；
- Canonical 1A-A/B/C/D 虽已完成共享契约和宿主门禁，四个只读 identity 仍为 `catalog_only + partial`，模型可见数为 `0`；
- `novel.read` 的多事实源、`structure.read` 的 version/active/CAS、`context.read` 的 summary/context bundle、`memory.search` 的 embedding/混合检索证据仍分别阻断 exposure；
- legacy Workbench/DSH 工具链尚未被 Canonical 投影替代；
- R4 真实 Main Agent Runtime、Writing/Context/Quality SubAgent 仍未放行；当前真实章节证据属于确定性 Writer 路径，不能据此宣称 DSH 结构化任务或自主整书编排已经验收。

## 15. 验收原则

未来实现至少满足以下产品验收：

1. 应用启动后首先进入创作工作台。
2. 用户可以在一本小说下创建两个任务，分别选择不同模型并同时运行。
3. “生成下一章”和“审计既有章节”不会共享或覆盖彼此的对话、取消状态和产物。
4. 四类关键工具调用按顺序显示在对话中，失败发生在哪一步就显示在哪一步。
5. 任务详情不依赖独立时间线、计划、工具或产物详情面板。
6. 完成的候选以产物卡片推送；普通文本回复不能直接修改正式事实。
7. 基线变化后，旧产物应用明确冲突，不能静默覆盖。
8. 章节候选未经对话确认不能进入审阅，未经显式采用不能成为正式正文。
9. 原写作工作台默认只读，编辑、保存、采用均为可区分的显式操作。
10. 待确认状态在任务树和对话中可找到，删除独立入口后不丢失可发现性。
11. 刷新或重启后能恢复任务、工具终态、产物和用户决定。
12. 全局并发、预算、凭据和 SQLite 权威边界保持有效。
13. “当前插件”视图与 Runtime Registry 一致，可查看功能、模型和其他插件，但不存在安装、卸载、启停、配置、更新或市场操作。
14. 重试不会新增重复用户回合；刷新后仍能看到原回合下每次 Run 各自的模型、工具、错误和产物。
