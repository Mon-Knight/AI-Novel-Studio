# v3.6.0 真实 UI 对话 6 万字验收报告

日期：2026-08-28  
版本：v3.6.0 本地发布候选  
模型：`openai_compatible / gpt-5.6-luna`

## 1. 验收范围

本次验收通过真实 Windows Tauri/WebView2 界面完成模型设置、章节生成、候选确认、人工审阅、保存和采用，并对最终 15 章正文进行逐章人工审读。

本报告把三类结论严格分开：

1. 工程闭环是否真实执行；
2. 原运行是否满足“单任务连续 15 回合”的任务拓扑；
3. 最终正文是否达到连续性和成稿质量要求。

真实模型不在本次文档任务中重跑。本报告不记录 API Key，不触发 Provider 请求，也不执行 Tauri、MSI 或 NSIS 打包。

## 2. 最终结论

| 验收面                 | 结论       | 边界                                                            |
| ---------------------- | ---------- | --------------------------------------------------------------- |
| 真实模型与 UI 工程闭环 | **通过**   | 15/15 章均完成生成、确认入审、保存和采用                        |
| 正文字数与持久化账本   | **通过**   | 独立采用稿、章节合计和小说缓存均为 61,396 字                    |

| 修复后的稀疏创意 Full  | **未通过** | 尚无按正式规划完成约 6 万字全部章节的通过证据                   |
| 小说内容质量           | **不通过** | 第 12～14 章存在互斥高潮、倒计时回跳、规则重置与伦理逻辑冲突    |
| 产品级最终验收         | **不通过** | 工程证据不能替代任务拓扑证据或内容质量                          |

```text

单任务连续创作 Full = NOT VERIFIED（尚未完成正式规划中的全部章节）

总体产品验收 = FAIL
```

## 4. 原运行拓扑纠正

原验收曾被概括为“仅通过一个创作工作台对话逐章完成 15 章”。复核运行时任务树与原执行路径后，该说法不成立：实际是每章新建一个 TaskConversation，共 15 个独立任务，每个任务完成一章。

脱敏导出只保留章节、模型、字数、哈希、正文和耗时，不保留 `conversationId / turnId / runId / artifactId`，因此不能用脱敏文件反向证明单 conversation。报告必须按真实运行拓扑记账，不能用章节数量代替回合连续性。

当前 [conversation-60000.spec.ts](../../tests/real-acceptance/conversation-60000.spec.ts) 已把主验收契约修正为：

- 默认 `sparse-idea` 从一句“约 6 万字的近未来悬疑小说”创意开始，用户不提供世界背景、人物、章纲或章节数；`prepared-assets` 仅作为可显式选择的独立夹具场景保留；
- 首轮必须形成并应用正式 `story_plan` 产物；测试从该不可变产物读取卷章顺序、章节数和目标字数，并逐项核对原子应用后的 SQLite 章节，不再把 15 章写进用户提示或稀疏验收期望；
- Gate 最多执行规划中的前 4 章，先覆盖至少三次跨章承接；Full 执行正式规划中的全部章节。第 2 章起切换目标章节并向同一 `conversationId` 追加“继续写”；
- 最终 conversation、run、artifact、决定和已消费审阅授权数量按正式规划推导出的实际执行章节数核对；每个 user turn 的指令哈希、turn/run/artifact 关联和目标章节必须逐一对应；
- 每章必须从生产写章工具事件读取 `contextHash` 与 `continuitySourceHash`，后者必须等于上一章真实采用稿的 SHA-256，测试侧不得自行回填该值；
- 证据必须保留任务、回合、运行和产物标识，避免再次把独立任务误记为连续对话。

以上契约已经取得一轮真实 Gate 证据，但不是本轮 61,396 字原运行的证据，也不能替代 Full。Gate 从空项目和一句“写个六万字左右的悬疑故事。”开始，在同一任务内自动准备并应用世界与规则、主角、全书规划，随后完成规划前 4 章；完整动态规划全程仍保持 `NOT VERIFIED`。

### 4.2 已完成的生产修复

- 写章服务会在每一章生成前读取紧邻前章的真实已采用正文，将章节 ID、草稿 ID、正文 SHA-256 和正文内容冻结进 generation context snapshot；模型必须承接其最终时间、人物、物件、伤势和系统状态，不得重演已发生事件。
- 当存在前章采用稿、ContextRecord、Memory、人物状态或地点资产时，快照会追加不进入公开摘要的内部连续性账本：相对时间先换算为稳定 `storyNow / deadlineAt`，章节切换不得重新起算“今天/明天/次日”，同时复核地点移动、物件归属、伤势左右侧/治疗状态及物理或数字系统状态。信息不足时保持模糊而不补造精确事实。
- 前章解析按“卷顺序 + 卷内章节顺序”执行，第二卷首章能够承接第一卷末章，不再把卷内 `orderIndex` 当成全书顺序。
- 超过上下文分区上限的前章正文保留开头和结尾，优先保住生成下一章所需的最终状态；快照改为持久化保存，工具事件只记录哈希和来源章节，不记录正文。
- 写章服务现在区分“真正首章”“前章尚未采用”和“采用稿正文不可读取”；后两种状态会在编译 Prompt 和调用模型前分别以稳定错误失败关闭，不再跳过连续性基线继续生成。
- 工具事件在追加 generation context 证据时保留原 `ToolResult` 的 `ok / artifactType / candidateOnly / data` 顶层契约，正文只投影长度；旧消费者不会因证据包装改变而失去结果字段。
- 公开 Tauri 对话命令和浏览器开发写入口拒绝客户端自报的 `toolCallingAttestation`；只有 DSH 在严格 nonce 探针通过后才能从 Rust 内部写入完整认证。耐久协议在 Web Crypto 不可用时也改为明确失败，不再用 FNV 短哈希冒充 SHA-256。
- 单个任务创建时固定模型；重试沿用原 Run 模型身份，浏览器回退与 SQLite 均拒绝中途换模。API Key 仍只存在当前应用进程内，并按 Provider、Base URL 和模型精确绑定。

这些修复已通过定向动态测试，但不能反向修复已经生成的 61,396 字正文，也不能替代下一次真实单任务验收。

### 4.3 新 UI 的真实使用结论

- 新 UI 已形成任务树、同轴对话流、底部 Composer、模型选择、内联工具事件和产物卡的桌面创作主路径；冷启动先显示稳定壳层，写作审阅区使用局部骨架，不再等待全部恢复任务后才首次渲染。
- Edge 浏览器布局已覆盖 1024×700、1440×900 和 2560×1440；最终 Windows Tauri/WebView2/SQLite 套件 18/18 specs、21/21 cases 通过。现有 61,396 字真实运行仍是 15 个独立任务，因此没有验证同一任务积累 15 个长回合后的滚动、重绘、内存和重启恢复体验。
- 第 9 章实际等待 237,888 ms 时，运行区只能表达“执行中”，不能区分等待首 Token、正常流式生成、上游重试或停滞。后续应显示真实 elapsed、当前阶段、最后活动时间和重试次数，但不能伪造百分比。
- 项目初次读取或 Bundle 切换时，当前 `WorkbenchPage` 会用整块加载面替换任务标题、消息流和 Composer。后续应保持任务树、Header 与 Composer 常驻，只让消息区局部进入骨架或错误状态，确保长任务切换期间草稿始终可编辑。
- 产物卡原先的“校验通过”只代表 ResultArtifact 的结构、来源和哈希有效，却容易被理解为正文质量通过；现已收窄为“结构与来源校验通过”。小说连续性检查必须作为另一项独立状态展示。
- 长对话仍会在 Bundle 刷新时读取完整 Artifact，折叠的正文也保留在 DOM 中。下一阶段应按展开或进入审阅时懒加载正文、按 artifactId 缓存，并默认折叠较早 Run。

## 5. 内容审读结论

### 5.1 阻断问题

1. 第 11 章倒计时从 `00:19:58` 走到 `00:18:41`，第 12 章却回到“还有四十七分钟”，并从馆长办公室无过渡跳到中央塔外。
2. 第 12 章已经完成“沈砚告别 → 选择归还 → 沈砚消失 → 升降梯上行”，第 13 章又从离线层重新执行同一组选择，属于两版高潮并存。
3. 第 13 章写“归还通道无法关闭、进度过半、全城回声涌出”，第 14 章又重置为“授权拆分、第一批/第二批/第三节点逐层释放”，系统状态和规则互斥。
4. 第 11 章规定手动终止需要三名原始授权者，后续没有补齐三人确认，也没有明确关闭永久擦除程序。
5. 第 12～13 章强制向全城归还记忆，第 14～15 章却以个人同意和选择权作为最终立论；接收者选择不能替代记忆主体的授权。
6. 陆惟川在第 13 章仍暴力阻止公开，第 14 章迅速转为留守赎罪，第 15 章又没有交代其生死、调查或问责结果。

这些问题集中在小说的高潮、因果规则和主题结论，不能按普通润色缺陷降级处理。

### 5.2 其他连续性与执行问题

1. 第 2 章把机械钟留在拆解现场，第 3 章开场却让顾闻舟直接托在掌心，中间没有取回动作。
2. 第 3 章结尾已经完成修船铺受伤和逃离，第 4 章开场又重新播放一次同类受伤与逃亡，推进被重置。
3. 顾闻舟母亲的名字先写成“顾若岚”，后续漂移为“顾青岚”，人物事实未锁定。
4. 第 8 章已经启动离线记录复制，第 9 章又重新插入接口并从 1% 开始，缺少失败、回滚或二次复制说明。
5. 第 8 章的幸存者始终使用男性指代，第 9 章开场却在没有身份变化说明的情况下改为女性。
6. 黑色纹路原本属于幸存者，第 8 章后段却无解释地转移到顾闻舟手臂，后文也没有收束其来源或影响。
7. 机械钟停在 `03:17:42`，官方事故时间为 `04:05`，相差应为 47 分 18 秒；第 3 章却写成“整整四十分钟”。
8. 同一官方事故在第 2 章记为 3 人失踪，第 10 章又变成 7 人失踪、32 人受伤，伤亡事实口径没有来源或修订说明。
9. 15 章中有 6 章偏离提示要求的 3,900～4,400 字区间：第 1、2、6、8、11、12 章；其中第 2 章为 5,138 字，超过提示中的 4,800 字硬上限。
10. 第 9 章耗时 237,888 ms，约为 15 章耗时中位数 64,142 ms 的 3.71 倍。最终成功不等于性能正常，后续需要记录首 Token、流式停顿、上游重试和分段耗时。

### 5.3 文本质量判断

- 开篇的空白航海日志与求救回声构成有效钩子；盐、锈、雾、机械钟和灯塔形成了稳定的意象系统。
- 沈岚的克制观察与顾闻舟的审慎回应具有可辨认声线，主要人物对话没有明显同质化。
- 第 15 章以厨房争执、太咸的鱼和无意义风声承载沈砚的生活记忆，沈岚从追逐完整答案转向接受不确定，人物弧成立。
- 沈岚与顾闻舟以互信、共同监督和边界意识收束，关系走向清楚。
- 全文未发现提示词、模型说明、TODO、Markdown 包装、乱码、完全重复段落或机械截断；第 15 章结尾完整。
- 全文共有 2,589 个段落、4,047 个句子。按标准化逐章正文统计加权，平均每段约 27.6 个字符、每句约 17.1 个字符；若直接用包含标题和换行的 `novel.txt` 总 Unicode 字符除以段落/句子数，则分别为 29.6 和 18.9，二者口径不可混用。对话段落字符占比约 28.8%。短段落适合悬疑推进，但第 12 章达到 236 段且平均每段仅约 22.3 个字符，高潮层次被频繁断行削弱，后续应合并只承载单一动作或反应的微段落。
- “像”出现 211 次、“忽然”46 次、“没有回答”20 次。稳定意象是优点，但相同比喻起手、突发转折和沉默反应反复承担节拍，会让不同场景呈现相似模板感；应在事件与事实连续性修复后再做语言层整理。
- 精确重复段落和跨章连续 50 字匹配均为 0，但第 12～14 章仍语义性重演同一选择与释放过程。这证明字符串去重只能排除复制污染，不能替代事件状态、规则和未完成动作的结构化一致性检查。

## 6. 后续门禁

再次申请最终验收前，至少需要：

1. 从第 12、13、14 章三套高潮中只保留一套，重建第 11～15 章唯一时间线；
2. 统一三授权者、永久擦除、归还通道和分批公开规则；
3. 让记忆主体授权、接收者选择和公共责任三层伦理保持一致；
4. 补齐陆惟川责任与城市恢复代价；
5. 增加生成后连续性门禁：抽取并核对倒计时、人物姓名与指代、物件和身体特征归属、事故伤亡口径、位置、伤势、系统进度和未完成动作，冲突时要求修改而不是直接采用；
6. 为高潮阶段冻结唯一事件状态机，后续章节只允许推进，不允许重新选择另一套公开/归还方案；
7. 将正式规划中每章 `targetWordCount` 推导出的允许区间作为可执行输出约束，超出或不足时先进行受控收束/补写，再进入审阅；
8. 按当前默认 `sparse-idea` 契约真实重跑：从一句普通创意生成正式规划，并在 1 个任务内完成规划中的全部章节；
9. 对新采用稿再次执行全书人工审读，再分别给出工程和内容结论。

在上述两条链路都通过前，不得把本轮记录改写为“真实单对话 6 万字最终验收通过”。
