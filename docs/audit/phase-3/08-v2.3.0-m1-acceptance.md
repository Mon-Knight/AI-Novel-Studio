## 2. `commands.rs` 差异解释

## 4. Migration 005～011 结论

- 顺序固定为 005 Task、006 Attempt、007 Input Snapshot、008 Context Snapshot、009 Constraint Snapshot、010 ResultArtifact、011 Validation Issue。
- 001～011 checksum 已由动态测试逐值固定，不再只检查 64 字符长度。
- 每项 migration 使用独立 SQLite transaction；当前项失败回滚，已成功的前序项保留。
- 真空库通过实际 `create_tables` 初始化；v2.2 账本从 005 顺序升级，二次启动幂等。
- 三类 Snapshot 禁止 UPDATE/DELETE；ResultArtifact 禁止内容更新和整行删除；Validation Issue 禁止 UPDATE/DELETE。
- 外键、唯一约束、关键索引和十个不可变/append-only trigger 均由动态测试发现并验证。
- 007～010 的不可变约束在 M1 正式验收前补齐并重新冻结 checksum；曾运行过验收前 M1 代码的开发数据库不属于发布兼容面，应删除后按最终迁移链重建，已发布的 v2.2 数据库可从 005 正常升级。

## 5. 三个迁移入口与四项 P0

- 设置连接测试：动态断言 `connection_test` 进入 `unifiedAiPipeline`，生成 generic text Artifact 并执行 exact `OK` 校验。
- 章节正文生成：动态断言 UI 入口进入统一管线后才创建候选草稿，Task/Artifact/source draft/version/hash 全部透传。
- 手动质量检查：动态断言 `useUnifiedPipeline=true` 不调用旧 `client.generate`，质量报告保存 Task/Artifact 身份。
- P0-1：精确采用显示的 draft ID/version/hash，不再查询 latest。
- P0-2：章纲、事件、章节总结候选在切章后保留预览但禁用写入。
- P0-3：质量修复只生成候选；确认前不采用草稿、不改 fixRun、不解决旧问题、不使上下文过期、不加载候选到正文。
- P0-4：章节总结只保存 Summary；context、character state 和 chapter status 衍生更新明确暂缓到后续安全应用阶段，不再吞错后形成部分成功。
