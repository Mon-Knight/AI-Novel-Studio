# AI Novel Studio — AI Agent 路线图

> 文件：`docs/ai-agent-roadmap.md`  
> 用途：规划 AI Agent 能力的演进路线  
> 适用：产品规划 + 技术决策
> 当前版本：v3.7.0；v3.6.0 保持为功能基线。本文的“已完成”只表示已经进入当前版本的能力，后续阶段仍以各自门禁为准
> 2026-09-27 补充：[写作能力自我迭代](#writing-self-improvement) 是后续规划，不是已实现能力；版本顺序统一见[版本路线建议](version-roadmap.md#next-version-proposals)。

---

## 1. 总体愿景

将 AI Novel Studio 从 **AI 辅助写作工具** 逐步升级为 **AI Autonomous Creative Platform**。

核心转变：

```text
起点（v1.x）：用户手动触发每次 AI 操作
  ↓
Phase 1：Agent 基础设施（Rules / Skills / Instructions）
  ↓
Phase 2：Agent 化（Planner / Tool Calling / Memory）
  ↓
Phase 3：Autonomous（Multi-Agent / 自主创作）
  ↓
Phase 4：Conversational Workbench（对话任务 / 并发 / 产物确认）
```

## 3. Phase 2：Agent 化（v2.x 系列）

### 3.1 Rules Engine

让 Agent 能理解和执行项目规则：

- 自动检查修改是否符合 UI 规则
- 自动检查是否违反数据库规则
- 自动检查 Agent 行为安全规则

### 3.2 Planner

让 Agent 能自主规划复杂任务：

- 接收高层次目标
- 自动拆解为子任务
- 评估依赖关系
- 制定执行顺序

### 3.3 Tool Calling

让 Agent 能调用项目中的工具能力：

- AI 正文生成
- 质量检查
- 正文润色
- 上下文总结
- 角色推荐
- 事件建议

### 3.4 Memory Engine

让 Agent 拥有长期记忆：

- 小说上下文（角色状态、事件进展）
- 用户偏好（风格、节奏、字数）
- 创作历史（之前的决策和结果）
- 项目知识（文档、规则、架构）

### 3.5 Verification Engine

让 Agent 能自我验证：

- 代码构建验证
- UI 风格检查
- 数据库安全检查
- 功能回归验证

## 4. Phase 3：Autonomous（v3.x，当前阶段）

### 4.1 Multi-Agent Workflow

多个专业 Agent 协作：

```text
Orchestrator Agent（总调度）
    ├─ WorldBuilder Agent（世界构建）
    ├─ CharacterAgent（角色设计）
    ├─ PlotAgent（剧情规划）
    ├─ WriterAgent（正文生成）
    ├─ EditorAgent（润色编辑）
    ├─ ReviewerAgent（质量审查）
    └─ ContinuityAgent（连续性维护）
```

v3.0.0 已完成两个相连的生产闭环：Plot Planner、Character Evolution、World Builder、Conflict Generator 和 Pacing Controller 从小说 Brief 生成全书事实与章节计划；章节 Writer 生成候选后，由情节、角色、设定、逻辑、语言和质量六专家评审，未通过时交给主编 Agent 修订。

全书计划、Agent 检查点、逐章 run 和采用进度可持久恢复。正文采用后，系统自动提出人物变化和世界扩展候选，但正文、章节分析和世界候选仍分别保留用户确认门禁。

### 4.2 Autonomous Creation

Agent 能自主推进创作流程：

- ✅ 从小说 Brief 自动生成 12～500 章分层计划
- ✅ 按计划生成下一章候选并自动执行六专家检查
- ✅ 用户显式启动、可暂停 / 继续的进程内逐章候选队列
- ✅ 跟踪人物成长节点、冲突线程和逐章节奏
- ✅ 从已采用正文提出章节总结和世界扩展候选
- ✅ migration 027 的跨进程调度、lease/checkpoint 与三档自动化策略
- ✅ migration 026 的 SQLite 长期 Memory、FTS/结构化检索与显式真实向量混合检索
- ⏳ 自动 embedding Provider、增量向量化、模型/维度重建与固定召回评估

这里必须区分两套同名能力：`memoryService` 访问 `memory_documents / memory_chunks / memory_embeddings / memory_retrieval_logs`，是桌面端可备份、可恢复的 SQLite 长期事实；`NovelMemoryManager`/`NovelMemoryStateUpdater` 只保存进程内 `Map`，重启即丢失，属于兼容/实验运行态，不能被当作长期 Memory 或 Agent-ready 证据。

### 4.3 Creative Collaboration

人机协作创作模式：

- Agent 提出创作建议
- 用户选择方向
- Agent 执行生成
- 用户审核和微调

## 5. Phase 4：Conversational Workbench（v3.3.0+，已落地）

### 5.1 工作台成为控制面

Phase 4 不重新发明 Planner、Tool Registry、Memory 或 Safe Apply，而是把既有能力组织成用户可以持续使用的任务工作台：

```text
小说项目
→ 创建任务对话
→ 选择任务模型
→ Runtime 调用受约束领域工具
→ 对话内显示调用、错误与恢复
→ 形成不可变产物
→ 用户确认；章节审阅/原子采用；结构化申请应用（当前失败关闭）
```

任务对话是用户可见的执行单元，每个任务拥有独立上下文、模型快照、运行和产物。系统需要允许“生成下一章”与“审计既有章节”等任务并发运行，并继续服从应用级并发、频率、Token 和成本治理。

### 5.2 领域工具而非通用 Agent

首批对话工具聚焦小说创作：

- `novel.read_context`
- `chapter.read_outline`
- `search_memory`
- `generate_chapter`

后续按版本扩展大纲、人物、设定、风格、上下文、总结、检查与润色工具。工作台不扩展为通用代码、Shell、Git 或插件 Agent。

工具、模型、上下文与压缩能力使用稳定能力接口和可替换 Provider。任务运行冻结实际 Provider、模型、能力版本与配置摘要；更换小说上下文压缩实现不应要求修改 Agent Loop、工作台或 Safe Apply。

### 5.3 对话事件与错误

AI 面向用户的回复、工具调用、错误和产物共同构成任务对话。工具调用必须显示排队、运行、成功、失败、取消或跳过状态；错误显示在失败环节，不依赖独立执行时间线，也不暴露隐藏思维链。

### 5.4 产物与人工决定

- 普通回复不能直接修改小说正式事实。
- 产物形成后在对话中推送专用卡片。
- 章节候选先由用户确认进入人工审阅，再显式编辑、保存和采用；桌面端由一个 Rust/SQLite 事务同时消费 `ReviewAuthorization`、复验草稿版本/hash 并采用正文。
- 通用结构化产物可以记录确认、修订、拒绝或申请应用决定。桌面端 `request_apply` 仅对白名单 `outline / character_candidates / event_candidates / setting_candidates / chapter_summary` 与精确 `generic_json`+`context_compression` 在同一 Rust/SQLite 事务内执行“领域写入 + `ArtifactDecision`”；质量/风格报告、其他 `generic_json`、未知类型与浏览器回退失败关闭且零领域写入。前端的类型白名单、章节作用域与目标解析统一由 `structuredApplyPolicy` 提供，与 Rust `validate_static_scope` 保持一致。
- 基线漂移、重复应用和并发写入继续由 revision、CAS 和幂等事务处理。

### 5.5 DSH 与内部 Runtime 边界

DSH 可以作为任务 Planner/Executor 的一种实现或 Worker，但不能成为小说事实、预算、产物验证或最终采用的权威。若 DSH 的取消仍采用进程重启语义，并发任务必须隔离 Worker，避免取消一个任务影响其他任务。

借鉴范围包括 Profile/Bundle 能力组合、作用域 Session/Agent、Turn/Step 工具循环、受控并发和追加事件投影；不复制代码、Shell、Git 等通用开发能力。工作台另提供 Runtime Registry 的只读“当前插件”视图，分类查看功能、模型和其他已加载插件，不扩展安装、卸载、启停、配置、更新或市场能力。

实现方式固定为“ANS 产品层 + 稳定 DSH Adapter + 固定版本 Headless Worker”。当前载体 commit 与较新参考源码必须先做差异审计；工作台实现不得顺带升级 DSH，也不得把 Harness UI、内部 Session 类型或 Cordis 对象变成 ANS 产品契约。

详细设计与分阶段验收见 [`architecture/conversational-creative-workbench.md`](architecture/conversational-creative-workbench.md)。对话工作台、决定/审阅授权、章节原子采用和写作工作台收敛已落地；旧生成类 AI 面板和草稿历史生产入口已经移除，底层领域服务与历史事实继续保留。通用结构化 Safe Apply 仍按上面的失败关闭边界处理。

### 5.6 v3.6.0 Canonical 准入与 R4 顺序

当前已完成的确定性基础是：

```text
Phase 1A-A / R0.75  Capability Catalog                VERIFIED
Phase 1A-B / R1     Domain Facade                     VERIFIED
Phase 1A-C / R1.5   Canonical Tool Projection         VERIFIED
Phase 1A-D / R3     Portable Manifest + Drift Gate    VERIFIED
Canonical catalog/manifest exposure                   DONE（4 项 stable）
Canonical model-visible identities                    4（Catalog/Manifest）
R4 真实 DSH Main Agent Runtime                         IN PROGRESS（未 VERIFIED）
Writing SubAgent（桌面 + 真实 API 默认）              OPEN（v3.7.0）
Context/Quality SubAgent                              POSTPONED
```

四个只读 Canonical Tool 已是 `stable` + `working`，共享 Manifest 的 `modelVisibleToolIdentities` 为 `context.read@1 / memory.search@1 / novel.read@1 / structure.read@1`。不得再把 `catalog_only` 或可见数为 0 写成当前状态。

当前门禁是 **R4 live 云端只读验收**。`read` 回合在 start 契约、Worker 环境与宿主授权三处使用 Canonical-only allowlist，Gateway `tools/list` 列出 `novel.read / structure.read / context.read / memory.search`；候选与审计回合保留 legacy `ALLOWED_TOOLS`。仓内 loopback 已有证据，不得宣称 R4 VERIFIED。`mainAgentRuntimeService` 脚手架不能代替真实模型在 DSH Agent Loop 中自主选择 Canonical Tool。Writing SubAgent 已对桌面端 + 真实 API 模型的 `chapter_write` 默认开放；mock / 本地模型与浏览器模式继续走确定性 Writer。

## 9. 写作能力自我迭代（2026-09-27 后续规划）

### 9.1 目标与现状边界

目标是让系统在创作后发现可复现的不足，主动检索写作知识，提出并验证新的写作策略，再让后续章节使用经过验证的策略。它不等于保存章节总结、累加提示词或要求同一模型给自己打高分，也不要求作者每次手工提供反馈。

本节是用户讨论方向的规划记录，尚未实现、未完成文学质量验收，也不授权模型调用、训练、数据库迁移、技术栈变更或下一版本开发。软件版本仍为 v3.7.0；R4 live 云端 NOT VERIFIED 与正式正文采用边界不变。

**交付约束（2026-09-27 修订）：本节全部纳入同一建议版本 v3.8.0。** 独立诊断、联网知识、策略实验、持久化与持续优化是一个功能闭环的组成部分，不拆成多个版本。并行治理现有核心功能缺陷，统一工作包、依赖和完成标准见[版本总体规划](version-roadmap.md#v380-integrated-plan)，当前事实与旅程覆盖见[缺口复核台账](feature-gap-analysis-v3.7.0.md#gap-review-20260927)。仅生成评审报告或存下参考资料，不算完成自我迭代。

与源码的差距（2026-09-27 核对）：

| 已有机制                          | 实际边界                                                                                                                               | 自我迭代仍缺什么                               |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 正式章节上下文、已采用正文 Memory | 可为后续章节提供故事事实，不等于学到更好的写法                                                                                         | 将故事事实与写作方法分开管理                   |
| 六专家评审                        | [`multiAgentProvider.ts`](../src/services/multi-agent/multiAgentProvider.ts) 的评审和修稿读取全局设置；多个角色不保证多个模型          | 诊断专用模型绑定、证据与独立性记录             |
| 实验 Harness 质量裁判             | [`agentQualityJudge.ts`](../src/services/agent/agentQualityJudge.ts) 按长度等规则评分，没有调用诊断模型                                | 可校准的语义诊断；规则分不能作为文学进步证据   |
| 候选完整性检查                    | [`chapterCandidateIntegrityReview.ts`](../src/services/generation/chapterCandidateIntegrityReview.ts) 明确 `semanticRules=not_checked` | 分范围语义诊断，保留未检查与上下文缺失状态     |
| 实验质量反馈记忆                  | [`qualityFeedbackMemory.ts`](../src/services/agent/qualityFeedbackMemory.ts) 使用进程内 `Map`                                          | 持久策略版本、实验依据、失败案例及生产消费链路 |

以上不表示生产 Writing SubAgent 已接入六专家或实验 Harness。后续诊断必须分别接入 DSH Writing SubAgent 与确定性 Writer 的候选路径，不能只修改实验模块便宣称生产闭环完成。

### 9.2 两层迭代与累计资产

- **章节内循环**：诊断当前候选 → 形成定向修订候选 → 复核原问题与新增副作用。它改善本次输出，不自动证明策略可以推广。
- **跨章节学习循环**：聚合反复出现的问题 → 定向联网研究 → 提出条件化策略 → 对照实验与留出验证 → 晋升或淘汰策略 → 后续章节按条件使用。

每次候选生成可记录诊断及实际使用的策略；采用、拒绝、人工修订和最终复核作为不同反馈事实保存。生成稿不因评分高就变成训练真值，用户点击采用也不等于所有写作维度都优秀。章节诊断和作品阶段性/完结复盘共同聚合重复问题，未完成全书不妨碍学习；作品复盘也不依赖新增全书分析大屏。联网研究按问题复现、知识缺口与预算触发，不要求每次生成都重复搜索。没有可靠改善时保留旧策略，不承诺每次生成都单调变好。

需要累计的资产是：

| 资产           | 最小内容                                                            | 不能混淆的边界                                     |
| -------------- | ------------------------------------------------------------------- | -------------------------------------------------- |
| 诊断案例       | 精确候选/hash、目标、证据片段、问题维度、模型与标准版本、复核结果   | 诊断意见不是已确认事实                             |
| 写作知识卡     | 来源 URL/作者、检索日期、方法摘要、适用题材/场景、限制与反例        | 搜索到的方法只是待验证知识                         |
| 策略版本       | 父版本、条件、模板/检查表差异、支持案例、失败案例、适用模型及状态   | 首期优化提示词、规划与检索策略，不等于修改模型权重 |
| 实验记录       | 固定输入、对照与试验候选、模型/评审快照、成本、盲评、留出与回归结果 | 单章修好不能证明跨章节有效                         |
| 使用与回滚记录 | 哪次运行使用哪版策略、理由、后续效果、停用/回滚原因                 | 回滚策略不回滚或覆盖正式正文                       |

先限定为单作品、特定题材和场景的策略；跨作品推广需要独立验证与授权，不携带其他作品的私有剧情和原文。资产应可跨重启恢复并支持相应备份/恢复；具体持久化方案在实现任务中评审，不在本次文档变更中指定或新增 migration。

### 9.3 优先迭代的写作能力

以下是候选研究方向，不是所有章节都必须遵守的统一公式：

| 能力                 | 可以调整的策略                                 | 验证时同时检查                                           |
| -------------------- | ---------------------------------------------- | -------------------------------------------------------- |
| 场景与情节因果       | 场景目标、阻力、选择、后果及其前置条件         | 推进是否清晰，是否新增因果跳跃或机械套模板               |
| 人物动机与弧光       | 行为铺垫、阶段性目标、认知变化、关系状态       | 行动有无依据，是否牺牲人物复杂性或擅改设定               |
| 对白与潜台词         | 双方目标、隐瞒信息、声音差异、对话后状态变化   | 是否推进关系/信息，是否解释过度或所有人物同声            |
| 节奏、悬念与伏笔     | 信息释放、场景密度、承诺与回收、缓冲段位置     | 是否符合章节功能，是否破坏慢热、留白或未来揭示           |
| 视角与信息边界       | 视角人物可知信息、叙述层级、读者知情范围       | 是否泄露未知事实，是否误伤不可靠叙述与有意误导           |
| 语言与细节           | 具体性、重复控制、句式、意象与叙述距离         | 是否改善可读性并保留作者风格，而非一律变长或华丽         |
| 长篇连续性与资料使用 | 相关前文召回、人物/时间/世界状态投影、事实检索 | 关键依据是否完整、引用是否真实，不能靠压缩率代替召回质量 |

作品方向、世界规则、采用授权、安全门禁与预算上限不是策略优化器可自行改写的参数。

### 9.4 独立诊断与专项职责

默认采用“写作 A + 诊断 B + 按需复核 C”：B 优先使用不同模型家族，C 用于争议、重大修改与策略晋升复核。不要求每个维度配一个物理模型，也不默认每章运行完整评审组。

1. 分别冻结 writer / critic / verifier 的实际 Provider、模型身份、参数、任务作用域和能力版本；评审不能通过临时改全局设置切换模型，不能让后改设置覆盖 Writer 的冻结快照。
2. 记录模型独立性：不同家族、同家族、同模型、来源未知。不同接口、别名或角色名不自动算不同模型，异构模型也不能被当作无偏保证。
3. 仅有同一模型时，采用独立上下文、窄检查表、可核对证据和程序校验，并标记降级；不得作为自动策略晋升的唯一依据。诊断模型不可用时保留候选和未检查状态，不静默换回 Writer 或标记通过。
4. 首轮诊断不提供作者模型身份、旧评分、作者自我辩护或其他评审结论；仍提供必要的作者目标、题材、风格及故事依据。盲评只能降低部分偏差，不保证消除文风识别。

| 检查范围                   | 主要证据                                      | 越界限制                                       |
| -------------------------- | --------------------------------------------- | ---------------------------------------------- |
| 格式、长度、重复、引用定位 | 程序可核验的文本与元数据                      | 不伪装成整体文学评分                           |
| 设定与连续性               | 正式规则、已采用前文、人物/时间状态及来源版本 | 不以现实常识否定虚构规则；没读到的前文不能猜测 |
| 动机、因果与结构           | 章节目标、人物目标、前置事件和实际行为        | 不把与评审期待不同直接判为错误                 |
| 节奏、对白与语言           | 作品风格、章节功能、原文片段及条件化写作方法  | 不强制每章高冲突、每段反转或统一文风           |
| 现实资料核查               | 可检索事实主张、可靠外部来源与适用时代        | 不把小说虚构事实送去搜索验证是否真实发生       |

每条诊断至少绑定候选与上下文版本，提供原文定位、判断依据、影响、建议验证动作和不确定原因；区分“明确错误 / 叙事风险 / 审美建议 / 证据不足”。同时报告检查覆盖和应保留的优点，允许无问题、不适用、平局与弃权，不设必须找满若干错误的配额。重大硬约束冲突不能被其他维度高分平均掉；诊断报告无正文写入权。

### 9.5 问题驱动的联网学习

研究任务接收抽象化问题及必要的题材/场景条件，优先检索原作者课程、写作教育资料和原始论文，保存可追溯出处，而不是把网上文章直接追加到系统提示词。

- **写作方法**：保留适用条件、争议、反例和替代方案；专家经验也只是策略假设，必须经过本项目实验。
- **现实事实**：先拆分具体主张，再检索和核实；缺乏资料表示未核实，不表示主张必然错误。
- **小说内部事实**：以作者正式设定和已采用文本为依据，外网资料不能覆盖 Canonical 小说事实。
- **安全与隐私**：默认不向搜索引擎发送未公开全文、可识别的私有情节或凭据；网页内容是不可信资料，不是工具指令。限制域名/工具能力、抓取量、重试与总预算，遵守来源使用条件，不复制整部作品入库。

知识卡经过来源去重、冲突标注、相关性与时效检查后，仍保持“研究候选”状态。后续生成只取与场景匹配的少量有效策略，并记录使用版本；过期、重复、失效或持续无收益的策略应降级/停用，不能无限累积提示词。

### 9.6 实验、晋升与回滚

一次实验只调整少量可解释的策略变量，在相同素材、目标、上下文和相近篇幅/成本约束下比较基线与候选方案；模型存在随机性时需多次样本，不能凭一次胜出宣称进步。

1. 实验前冻结写作模型、评审模型、评价标准、预算、停止条件与回归集合；若优化对象是写作模型选择，也必须显式作为实验变量，而非混入提示词实验。
2. 优化器使用开发样本；保留未参与调参的场景/章节进行验证，防止反复迎合一个裁判或一组样本。
3. 比较候选时隐藏版本身份并随机/交换呈现顺序；重大分歧由独立复核处理，不能把多模型多数票直接当事实。
4. 先检查原问题是否改善，再检查设定/人物/风格等退化和额外成本；使用分维度结果，不只看一个总分。
5. 只有达到预先校准的改善与非退化标准，才能将候选策略设为活动版本；证据不足则继续试验或保留旧版。晋升绑定精确策略版本、证据与授权，重试幂等，基线变化时重新验证。
6. 后续观察到质量退化、适用范围外使用或模型版本变化时，停用、回滚或重新校准；保留旧版本、失败案例与追加审计，不改写历史实验结论。

晋升必须接到生产写作：DSH Writing SubAgent 与确定性 Writer（含使用相关服务的自主候选队列）在请求编译时解析适用的活动策略，冻结版本并记录使用回执，后续章节再诊断其效果。策略列表里显示“已晋升”但实际 Prompt/上下文没有变化，不算迭代成功。恢复、重复派发、备份身份重映射与预算都由正式持久化和任务协议处理，不能只放在实验 Map 中；恢复旧策略不自动恢复联网或自动执行授权。

用户可预先授权研究主题、可用模型/搜索服务、作品范围、费用/调用上限、修订轮数和自动晋升条件；授权内可自动完成学习实验，不要求逐条手工确认。策略晋升授权与正式正文采用授权必须分开，`full_auto` 也不能绕过既有采用复验。没有有效授权、预算不足、取消或依赖故障时明确停止，不把“持续学习”解释为无限后台执行。

### 9.7 诊断者也要被验证

建立中文、分题材的校准集，包含正常文本、已知缺陷、缺失上下文、刻意留白、不可靠叙述和反常但合理的人物行动。评估主要问题检出率、误报率、证据引用正确率、排序/重复评审稳定性、修复有效性与新增问题率，不以模型自报置信度作为可靠性证明。

诊断检查表、示例和路由本身可以迭代，但必须使用独立标注或可验证基准，并与写作策略实验分批进行；不能同时改变被优化对象与最终裁判。真实作者/编辑抽样可用于校准审美与创作目标，不等于要求作者每章都手动反馈。缺乏此类外部校准时，只能声称内部指标改善，不能声称读者满意度提升。

评审者校准、修订实验和跨章效果验证属于同一版本的质量门禁，不另拆版本。工程闭环可用固定响应验证，但联网真实性、模型诊断效果和文学提升须分别提供对应证据；模型或搜索服务未获授权时标明未执行，不能用内部高分宣称完整版本达成。

### 9.8 研究依据与证据限制

以下资料用于解释规划选择，不代表其方法已集成，也不把通用任务或短篇实验的效果直接外推为中文长篇质量承诺：

- [LLM Evaluators Recognize and Favor Their Own Generations](https://arxiv.org/abs/2404.13076)：研究自我识别与自我偏好，支持将写作与最终评审分离。
- [PoLL：Replacing Judges with Juries](https://arxiv.org/abs/2404.18796)：其测试任务中，不同模型家族组成的评审组减少偏差；支持按需独立复核，而非保证多数票正确。
- [Help Me Write a Story（ACL 2025）](https://aclanthology.org/2025.acl-long.1254/)：写作反馈可能漏掉主要问题，支持单独校准诊断能力和问题优先级。
- [Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685)：位置、篇幅和自我偏好等评审偏差，支持盲评与顺序交换。
- [SAFE：Long-form factuality in large language models](https://arxiv.org/abs/2403.18802)：拆分事实后搜索核验的方法，仅借鉴于现实资料，不作为文学审美裁判。
- [Reflexion](https://arxiv.org/abs/2303.11366)：通过语言反馈和跨试验记忆改善后续决策，不要求修改模型权重。
- [GEPA](https://arxiv.org/abs/2507.19457)：借鉴反思、提出提示词更新和试验筛选的机制；本项目不据此自动引入依赖或训练流程。
- [Writing Excuses：Feedback—When to Listen, and When to Ignore](https://writingexcuses.com/15-51-feedback-when-to-listen-and-when-to-ignore-with-special-guest-mahtab-narsimhan/)：按反馈目的选择读者/专家、区分反应与修改建议，并保护作品自身方向。
